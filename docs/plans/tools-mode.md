# Tools mode: a local package that does the mechanical work

Status: proposed 2026-11-23. Phase 0 done: the case harness is in [`tests/cases/`](../../tests/cases/README.md) and the [chat-mode baseline](../../tests/cases/baseline.md) is recorded. Decisions needed are listed in Section 10.

## 1. The idea

AI4SG Finder keeps one project with two ways to install it:

- **Chat mode** (today): the prompt and reference files in a Custom GPT, Gem, Claude Project, the one-click links or the all-in-one file. Every rule is an instruction the model may or may not follow. Nothing to install.
- **Tools mode** (new): a Python package that runs a local MCP server for Claude Code, Claude Desktop and other MCP clients. The model still interviews and writes; code fetches only the reference text each turn needs, checks drafts, runs the replays on local files and saves sessions. Where the client allows it, hooks make some checks compulsory.

The line between the modes is *local tools or not*, not the vendor. A hosted server that ChatGPT or others could reach would route users' details through a service the project runs, which undoes the privacy gain; it is out of scope.

## 2. What each mode guarantees

| | Chat mode | Tools mode in Claude Desktop | Tools mode in Claude Code |
|---|---|---|---|
| Instructions | 8,000-character prompt, plus knowledge files where the platform allows | No limit; loaded as needed | Same |
| Reference text per turn | Everything, or the platform's retrieval | Only the sections the turn needs | Same |
| Citation and figure check | Requested | Model is told to call the checker | A hook runs the checker on each reply and sends a failing reply back for revision |
| Format check (opening lines, headings, length) | Requested | Model-called | Hook-enforced |
| Records about named people | The model is asked not to use them | Read from local files; only totals reach the model | Same, and a hook stops a typed message that contains phone numbers or ID-like strings before it is sent |
| Replays and cost of ownership | Excel workbooks, by hand | Run on a local CSV by a tool | Same |
| Session record | Written on request | Saved to and loaded from a local file | Same |

The README's *Which way to use it* table gains a *Mode* column, and this table goes into the docs so users can choose knowingly.

## 3. Principles

1. **One source of truth.** The taxonomy and playbook stay the reference files for both modes. The package ships a copy that `scripts/build.py` generates and `--check` verifies, as it does for `dist/`.
2. **Chat mode doesn't change.** Its prompt and limits stay as they are; tools-mode instructions live in their own file, not as "if tools are available" lines in the shared prompt.
3. **Local and read-only.** The server makes no network calls, reads only files the user names, writes only to its own session folder, and never runs anything it reads.
4. **The model reads and writes; code checks and counts.** Interpreting answers and tailoring the recommendation stay with the model.
5. **Measure before building more.** Each phase ends with the worked cases run in both modes; the next phase starts only if the numbers justify it.

## 5. Tools

| Tool | Input | Returns | Notes |
|---|---|---|---|
| `get_section` | A class number, follow-up number, "decision tree", "funder review", "simpler options" or another named section | That section's text, plus the class's rows from cross-cutting tables (deployments, simpler option, tools, setups) | Replaces loading the whole 170,000-character file |
| `check_draft` | The draft and its kind (recommendation, follow-up, funder memo) | A list of problems | Citations not in the verified lists or the setups table; figures next to a cited name that don't appear in its reference entry (a heuristic, flagged as such); missing opening lines or headings; length over the target; any request for records |
| `run_replay` | Workbook (pick N, weekly visits, waitlist), a CSV path and the settings | The same results table as the workbook | Columns as in the workbooks; columns that look like names or phone numbers are refused, not read |
| `health_check` | A CSV path and thresholds | The one-page report | As workbook 4 |
| `cost_of_ownership` | A CSV of cost lines and settings | Totals, cost per extra person, lines still blank | As workbook 5 |
| `save_session` / `load_session` | A session record | Saved path / the record | Local folder only |

The interview's branching stays with the model in the first release. Moving it into code (a state machine read from a data file that `build.py` also uses to write the prompt's filter questions) is Phase 4, and only if the case runs show the model getting the branching wrong.

## 6. Tools-mode instructions

`prompt/tools-mode.md` starts from the system prompt and adds what chat mode had to cut or leave out:

- the cuts made to fit 8,000 characters (naming landmark research groups, the note that tutorial figures are illustrations, fuller heading descriptions);
- naming the replay workbook and the cost worksheet in the recommendation itself;
- when to call each tool: `get_section` before answering from reference material, `check_draft` before sending any recommendation, follow-up or memo, and fixing what it reports;
- never asking for records, and offering the replay tools on a file instead.

It is served by the server as an MCP prompt and copied into the plugin's skill, so the model gets it without the user pasting anything.

## 7. Enforcement through hooks (Claude Code)

The plugin adds two hooks; the exact hook events and their input format must be checked against Claude Code's documentation when they are built.

- **Before a message is sent:** scan what the user typed for phone numbers, ID-like strings and email addresses. If found, stop the message and explain that records should be read from a file with the replay tools. This is the only way in this design to keep records away from the model, and it works only in Claude Code.
- **When the assistant finishes a reply:** run `check_draft` on it. If it fails, return the problems so the model revises the reply before the user relies on it. Cap revisions at two to avoid loops.

Claude Desktop extensions can't run hooks, so there the checks depend on the model calling them; the guarantees table says so.

## 8. Testing and measurement

- **Unit tests:** the section parser (every class and follow-up found), the checker (known-good and known-bad drafts from past runs), and the replay and cost code against the results already verified in Excel (the same figures the workbook checks used).
- **The case harness in the repo:** it runs the 25 cases in chat mode (all-in-one) and tools mode, records input and output tokens per turn, and grades each run against the cases' expected outcomes and the cases-index checklist.
- **CI:** unit tests and `build.py --check` on every push; the case runs by hand before a release, since they cost tokens.

**Success criteria for Phase 1**, measured on all 25 cases:

1. Outcomes at least as good as chat mode on every case (same class or verdict, Case 6 still "no model needed").
2. No unverified citation in a final reply in Claude Code (hooks on).
3. At least 50% fewer input tokens per session than the all-in-one file, and no higher list-price cost per case than the baseline. The baseline found 98.3% of input tokens were cache reads, so the money saving with Claude is likely small; the token gain matters most without caching.
4. No case where the checker sends a correct reply back more than once.

If 1 or 2 fail, fix before Phase 2. If 3 fails, the token case is weak and the package rests on the checks alone; reassess.

**Baseline (Phase 0).** 24 of 25 cases reached their expected outcome; Case 15 put Class 3 first after skipping the narrowing question. Each turn read about 63,000–72,000 tokens; an interview case cost about US$1.17 at list prices and a funder review US$0.12. Details in [baseline.md](../../tests/cases/baseline.md). Case 15 is a direct test for the interview steps in code (Phase 4).

## 9. Phases

| Phase | Builds | Ends when |
|---|---|---|
| 0. Baseline | Move the case harness into `tests/cases/`, add token logging, run all 25 cases in chat mode | A baseline of outcomes and tokens per case is recorded |
| 1. Core | Package skeleton, `get_section`, `check_draft`, tools-mode instructions, plugin `.mcp.json` and the two hooks | The success criteria above are met in Claude Code |
| 2. Local data | `run_replay`, `health_check`, `cost_of_ownership`, sessions; parity tests against the workbooks | Each tool matches its workbook on the sample data |
| 3. Desktop and docs | The `.mcpb` extension, the README mode table and guarantees table, release attachments | A clean install in Claude Desktop runs Case 1 end to end |
| 4. Optional | Interview state machine; a standalone local app that owns the conversation loop | Only if Phase 1–3 measurements show a need |

## 10. Decisions needed

1. **Package name and where it's published**: PyPI as `ai4sg-finder`, or install from GitHub only.
2. **Install route**: `uvx` (no virtual environment to manage) or `pip`; minimum Python version.
3. **Whether to ship the Claude Desktop extension** (Phase 3) or support Claude Code only at first.
4. **Whether the hooks are on by default** in the plugin, or opt-in.
5. **Whether the case harness's token-costing runs belong in the repo's release checklist.**

## 11. Risks

- **The modes drift.** Mitigated by one set of reference files, the guarantees table and running the cases in both modes before each release.
- **Maintenance grows.** The project gains Python packaging, tests and a protocol to follow as it changes. Keeping the server small and read-only bounds this.
- **The checker is wrong.** Citation matching is reliable against fixed lists; the figure check is a heuristic and will miss some errors and flag some correct text. Its messages say which.
- **Over-engineering, by the project's own test.** The Claude skill already loads references on demand. Tools mode earns its place only through what the skill can't do: enforced checks, records kept local, replays on files and measured regressions. If Phase 1 doesn't show those gains, stop there.
- **Audience.** NGO program staff will mostly stay in chat mode. Tools mode is for technical partners, funders' analysts, intermediaries and maintainers; the docs should say so and not push program staff toward an install.

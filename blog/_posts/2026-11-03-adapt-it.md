*Part 6 of 6 in a series on [AI4SG Finder](https://github.com/ashitpatel/ai4sgfinder).*

AI4SG Finder is not an authoritative tool, and it shouldn't be the last word on any program's decision.

It's a starting point: a structured conversation that helps an NGO or public agency name its problem, see which methods fit, and know what to ask a technical partner. This last post in the series is about its limits, and about how anyone can do better.

## Where it can go wrong

- **It recommends an approach; it doesn't build the model.** Putting a method into practice still needs an operations-research or machine-learning practitioner, and a pilot.
- **It can misread a situation.** It knows only what you tell it in a short interview. A program with an unusual constraint, or two decisions tangled together, may get the wrong recommendation.
- **It runs on a language model, and language models can state things that aren't true.** The prompt tells it never to invent a citation, deployment or statistic, and to mark anything it isn't sure of. That reduces the risk; it doesn't remove it. Check every citation against its source before using it in a proposal.
- **The evidence will age.** New deployments will be published, tools and partners will change, and some of today's examples will be superseded.
- **Your field may need questions it doesn't ask.** It was built to work across impact areas, so it's general by design. A health ministry, a conservation agency or a microfinance network would each ask more specific questions.

## How it was built

I built AI4SG Finder, and wrote this series, by directing AI agents: I set the goals and made the editorial calls, and the agents did the research, drafting and checking.

So I've published the [prompts I used](https://github.com/ashitpatel/ai4sgfinder/blob/main/docs/building-from-scratch.md), rewritten from the requests that actually built it, with later corrections folded in. There are eight:

**Four for a chat assistant, to design it:**

1. **Is it worth building?** Does a tool like this already exist, and is it worth making one an NGO can run itself?
2. **Map the methods.** Survey the research and group allocation approaches into classes, built from the ways allocation problems differ, so coverage doesn't depend on which papers turn up first.
3. **Design the interview** and write the system prompt.
4. **Write the follow-ups** that come after a recommendation, from readiness checks to a brief for a technical partner.

**Four for a coding agent, to build and release it:**

5. **Package it** so it runs in Claude, ChatGPT, Gemini and browser assistants.
6. **Write the worked examples**: one case per class, a no-model case, and cases that combine two methods.
7. **Write the tutorials**, each with a program that measures the simpler alternative against the method. The prompt includes a template, so no example tutorial is needed.
8. **Release it**, after checking that every link resolves and every number in a tutorial matches its program's output.

Each prompt states its goal and audience, what to check and what to avoid, so an agent is less likely to drift.

## What you can do with them

- **Rebuild it and check my work.** If your version reaches different classes or different evidence, that's worth knowing.
- **Adapt it to your field.** Narrow the methods and questions to health, climate, education or another area, with the deployments that matter there.
- **Add what's missing:** methods, field deployments or questions the current version doesn't cover.
- **Translate it** for the communities and staff you work with.

Everything is open source under the Apache 2.0 license, so you can do all of this without asking.

## Tell me what you build

If you build a version for your context, or find where this one gets things wrong, tell me through an [issue on GitHub](https://github.com/ashitpatel/ai4sgfinder/issues). I'd love to link to adaptations from the project page.
